# 设计构型与文档管理：业务工作流梳理（rc2.45 第一阶段）

## 1. 使用者与他们要做的事

| 角色 | 系统角色 | 主要目标 | 最怕什么 |
|---|---|---|---|
| 设计工程师 | ENGINEER | 建文件、出版次、传附件、关联到件号、提交审核 | 流程绕、改一个名字要找管理员、不知道审批卡在谁那里 |
| 审批人 | APPROVER | 看清"改了什么"再批准发布 | 只看到一句变更说明，看不到附件到底变没变 |
| 构型管理员 | CONFIGURATION_MANAGER | 发布基线、作废文件、保证一个件号只有一份有效定义 | 已发布的对象被人悄悄解除主定义 |
| 系统管理员 | SYSTEM_ADMIN / DATA_ADMIN | 账号、字典、备份 | 无关入口太多、误点 |
| 生产 | PRODUCTION（新增） | 拿到**当前有效**的图纸/文件，直接下载 | 拿到草稿或已被取代的旧版本 |
| 采购 | PROCUREMENT（新增） | 按件号看有效资料、BOM、外部件，导出清单 | 同上；且不应拿到原生设计文件 |
| 只读查阅（原有） | VIEWER | 查阅全部数据（行为不变） | — |

## 2. 文档（设计文件）生命周期

```
新建文件 → 新建版次(WORKING) → 上传附件 → 提交审核(IN_REVIEW) → 批准发布(RELEASED, 内容冻结)
                                   ↑                │
                                   └── 退回/取消 ────┘        新版次发布后，旧版次 → SUPERSEDED
文件本身：ACTIVE ⇄ OBSOLETE（作废后不再出新版次；已发布版次与已冻结基线不受影响）
```

系统里早已成立、本次**不改**的硬规则：
- 文件身份与版次分离；同一文件同时只有一个未发布版次。
- 已发布版次内容冻结（数据库触发器）；发新版次不会自动改变任何件号的技术状态（INV-014）。
- 提交人不能批准自己的申请。
- 附件带 SHA-256，可做完整性巡检。

## 3. 本阶段发现的缺口，以及处理

| # | 缺口（用户视角） | 处理 | 位置 |
|---|---|---|---|
| 1 | 文件建错名字改不了 | 新增"修改名称"，记审计；文件号、类型不可改 | `PATCH /files/{n}` |
| 2 | 文件不再使用没有出口 | 新增"作废/恢复"，需理由、限构型管理员；有未完成版次、或仍是已发布对象的主设计定义时拒绝 | `POST /files/{n}/obsolete` `…/reactivate` |
| 3 | 审批人看不出新旧版本差在哪 | 新增版次对比：按附件用途逐项列出 新增/移除/内容已变/未变（按 SHA-256 判定） | `GET /files/{n}/compare` |
| 4 | 不知道一份图纸被谁用 | 新增反查：被哪些设计对象关联、被哪些基线锁定到哪个版次 | `GET /files/{n}/where-used` |
| 5 | 关联建错了没法撤销 | 新增"解除关联"（软停用，保留历史）；已发布对象的主设计定义不得直接解除（INV-022）；解除后可重新关联 | `DELETE /definitions/{id}` |
| 6 | 文件列表只能按关键词找 | 增加类型、状态、版次进展（已有发布/进行中/尚无发布）过滤，并显示进行中的版次 | `GET /files` |
| 7 | 生产、采购要找有效资料，得翻"设计资料清单"里混着草稿和旧版 | 新增**发布资料库**：只列当前有效的已发布版次，默认只看发布版 PDF，一键下载；作废文件不出现 | `/library` |
| 8 | 只读账号的菜单里有"备份恢复""系统管理" | 菜单按权限显示；备份页补上路由权限 | `app.js` |
| 9 | 文件详情页找当前有效文件要点三层 | 详情页顶部直接给出"当前有效版次"和附件下载 | `file-mgmt.js` |

## 4. 设计构型（基线）现状与下一阶段建议

已具备：基线的建立、条目锁定到具体版次、校验、提交审批、发布、基线对比、BOM 快照对比。

第二批已完成（同一 PR）：
1. **基线发布前检查**（基线详情页）：校验结果按类别分组——明细完整性、引用对象状态、附件完整性、外部件准入、与当前基线的差异；阻止项在前，每项带"去处理"直达链接。新增三条提示：引用了已作废文件、附件尚未做完整性校验、与当前基线内容完全相同（发布也不会带来变化）。原有 `errors/warnings` 字段不变。
2. **变更影响分析**（文件详情页，点开才计算）：这份文件关联到哪些对象、这些对象被哪些上层组件使用、哪些基线锁定了它；并标出"当前基线仍锁定旧版次"的情况——这是 INV-014 的直接后果，新版次发布不会自动改变任何件号的技术状态。
3. **件号资料包**（`/part/<件号>`，发布资料库里可直接输入件号查询）：当前基线锁定的有效文件（可直接下载）、BOM、外部件、软件，以及相对上一基线的变化；文件以**基线锁定版次**为准，有更新版次时明确提示；可导出 CSV（UTF-8 带 BOM，Excel 直接打开）。

4. **审批超期提醒**（阈值 3 天，常量 `OVERDUE_DAYS`）：审批人首页顶部红色提示"有 N 项审批已等待超过 3 天"，待办按超期优先排序并显示"已等待 X 天"；申请人首页提示"你提交的 N 项申请超过 3 天未被处理"，并列出当前卡在谁那里；审批中心两张列表新增"等待"列，超期标红。批准或退回后不再计入。

5. **生产、采购专用角色**（迁移 `0026_consumer_roles.sql`，权限在 `rbac.py`）：新增两个只读角色，并新增两项权限——`read_unreleased`（查看/下载草稿、审核中、已取消版次）和 `download_native`（下载原生设计文件）。**所有原有角色都保留这两项，行为不变**；生产、采购都没有，即：
   - 只能看到已发布（含已被取代）版次；下载草稿或原生文件按"不存在"处理（404），搜索、资料清单、文件详情、版次对比也同样过滤。
   - BOM、设计族、申请人草稿、基线历史、适用性、主数据批量导入导出、变更影响分析（含工作 BOM）返回 403；外部件、软件、发布资料库、件号资料包可用。
   - 左侧菜单只显示可用入口。账号管理里可直接勾选新角色。
   - 想让生产也能下原生文件：在 `rbac.py` 给 `Role.PRODUCTION` 加 `Perm.DOWNLOAD_NATIVE` 即可。
6. **版次全部附件 ZIP 下载**（`GET /revisions/{id}/download-all`）：按角色可见的附件打包，附 `SHA256SUMS.txt`；同名文件加用途前缀避免覆盖。入口在版次页、文件详情"当前有效版次"和件号资料包。

已知边界：数据质量、统计等汇总接口、外部件/软件接口仍对所有登录用户可读（生产、采购需要用外部件和软件）；本次的"只见已发布内容"覆盖附件、文件、版次、搜索、BOM 与基线历史。

## 6. 适航设计保证（DOA/CAAC）对照：三级签署（第三批）

背景：CAAC 管辖，图纸签署链为**编制-审核-批准**三级。已实现：

| 要求 | 实现 |
|---|---|
| 三级签署 | 提交=编制签署 → 审核人签署 → 批准人签署并发布；批准前必须审核已通过；任一级退回都回到编制，重新提交后三级重走 |
| 独立校核 | 编制、审核、批准必须是三个不同的人；由数据库触发器强制（INV-025/026/027），应用层之外也绕不过 |
| 有权签署人 | `signer_authorization`：谁、哪一级、哪类文件、有效期；只能撤销不能改删；不得自授权；提交和签署两个时点都校验（授权中途撤销，签署即被拒绝） |
| 电子签名 | 每一级签署都要重新输入本人口令；与登录共用失败计数和锁定策略，失败写审计（`SIGNATURE_AUTH`） |
| 签署记录 | `signature_record` 不可改删；固化签署当时的姓名/账户、时间、意见、方式，并绑定被签署内容的 SHA-256 摘要（版次+变更说明+全部附件） |
| 通知与待办 | 后序步骤在前序通过前不进任何人的待办、不发通知；审核通过时才通知批准人 |
| 历史数据 | 旧的单级已发布版次如实显示“审核：无此级（旧流程）”；升级前在途的单级申请仍可批准（需口令） |
| 模拟数据 | 演示/规模数据包用模拟身份走完整三级步骤，签署方式标为 `SIMULATION`，界面注明“模拟身份，非真人签署” |

未实现、仍待确认：
- **更改管理流程**（更改申请、分类、适航影响评估）——DOA 最实质的缺口，下一步。
- 有权签署人清单目前按“级别+文件类型”授权，尚未关联资质/培训记录、也不按产品或型号限定。
- 记录保存与归档策略、受控副本水印与分发确认、工具验证材料（需求—测试追溯矩阵）。
- 具体条款符合性需对照你们的设计保证手册和 CCAR-21 的适用要求，本系统只是支撑工具。

**升级注意**：升级后有权签署人清单为空，构型管理员必须先登记审核人和批准人，设计文件版次才能提交审核。这是刻意的——授权必须是明确的人为决定，系统不会按角色自动代授。
