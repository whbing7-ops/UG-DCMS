# DAS 运行与监控功能 — 设计输入清单

对应 UG-DAP-04《设计控制程序》第 3 步"设计输入的识别与确认"。本文件是把设计保证体系的
运行要求转成软件设计输入，**不是功能清单**。没有可验证判据的条目不算设计输入。

依据文件：UG-DAM-01 设计保证手册 00、UG-DAP-01～15 程序文件 00、UG-DAW-001～013 作业文件 00、
UG-DAF-00 表单汇编 00（含 21 张表单）、UG-DAM-01-附3 DOA 符合性检查单 66 条。

体量基线：**15 份程序 157 个工作步骤、97 类记录、21 张表单、19 项周期性活动、10 条法规硬时限。**

---

## 一、法规与局方要求（硬约束，不可协商）

这些不是需求，是边界。做错了不是"体验不好"，是不符合项。

| # | 输入内容 | 来源 | 可验证判据 |
|---|---|---|---|
| L1 | 故障、失效、缺陷自确认存在起 **48 小时**内报局方 | CCAR-21.5（六） | 计时口径必须是**日历小时**，含周末节假日；系统不得以工作日口径计算或顺延 |
| L2 | 局方一类问题 **21 个工作日**内落实措施，不得延期 | AP-21-18 | 计时口径是**工作日**；起算点是局方发布记录表之日；系统不得提供延期入口 |
| L3 | 局方二类问题不超过 **3 个月**，延期须届满前获批 | AP-21-18 | 延期必须记录局方同意的依据，无依据不得改期 |
| L4 | 内部独立监督计划周期 **≤12 个月**覆盖全部过程一轮 | AC-21-48 3.6(6) | 只能更短不能更长；系统不得允许配置 >12 个月 |
| L5 | 质量系统内部审核间隔 **≤12 个月** | CCAR-21.137（十四） | 同上 |
| L6 | 设计机构许可证有效期 2 年，期满前至少 **3 个月**申请延续 | AP-21-18 | 到期前提醒必须早于 3 个月，且不可关闭 |
| L7 | PMA 项目单有效期 2 年，失效后不得继续依据其授权活动 | CCAR-21.313 | 失效即冻结相关签署权，不是提醒了事 |
| L8 | STC 权益转让协议生效／终止后 **30 天**内通知局方 | CCAR-21.116 | 自然日计时 |
| L9 | 生产记录、检验试验记录及判定制造符合性所需资料**保存至产品永久退役** | CCAR-21.137（十三） | 到期销毁逻辑必须对这类记录失效 |
| L10 | 局方对本单位计划性监督至少 24 个月 1 周期 | AP-21-18 4.2 | 局方职责，本单位只需配合；系统记录不主动触发 |

**判据 L-总**：系统中任何一处倒计时，必须显式声明是"日历"还是"工作日"，且该口径不可由配置改变。
混用即为设计错误——UG-DAP-12 里专门写了"内部环节的工作日口径一律不得用于该 48 小时链"。

## 二、时限有三种，语义不同，不能用一个字段表达

这是最容易在实现时做错的地方，单列出来。

| 类型 | 例子 | 来源 | 行为 |
|---|---|---|---|
| **法规硬时限** | 48 日历小时、21 个工作日 | 上表 L1～L10 | 不可调整，超期即不符合项，必须留痕 |
| **内部时限** | 审核 ≤5 个工作日、CVE 核查 10 个工作日 | UG-DAW-001 第 3 章，**153 处** | 可调；调整只改 UG-DAW-001 一份文件，程序不动 |
| **触发式前置条件** | 发布前、交付前、首次使用前、改装前签署协议 | UG-DAW-001 | 不是倒计时，是"没做完不许往下走"的闸门 |

**判据 T1**：内部时限必须从一处（对应 UG-DAW-001）取值，不得散落在各模块代码里。
体系文件已经把这件事做到了——157 个步骤有 153 个写"见 UG-DAW-001"，软件不能倒退回去。

**判据 T2**：触发式条件必须实现为**阻断**，不是提醒。例如"未取得接收确认的资料不得用于改装"。

## 三、体系文件规定的流程（功能来源）

15 份程序不是 15 个模块。按**业务对象**归并后是这样：

| 业务对象 | 涉及程序 | 步骤数 |
|---|---|---|
| 符合性检查单条目 | 贯穿全部，UG-DAP-02/13/15 直接操作 | — |
| 岗位、任命与授权 | UG-DAP-03 | 11 |
| 项目（STC／PMA／受托） | UG-DAP-09、UG-DAP-04 | 20 |
| 设计对象与构型 | UG-DAP-04、UG-DAP-05 | 20 |
| 设计更改 | UG-DAP-06、UG-DAP-08 | 13 |
| 符合性验证 | UG-DAP-07 | 13 |
| 对外发布与持有人责任 | UG-DAP-11 | 17 |
| 事件报告（21.5） | UG-DAP-12 | 10 |
| 不符合项与纠正措施 | UG-DAP-14 | 10 |
| 独立监督 | UG-DAP-13 | 10 |
| 供应商与外部接口 | UG-DAP-10 | 13 |
| 局方往来与证件 | UG-DAP-15 | 7 |
| 体系文件与体系更改 | UG-DAP-01、UG-DAP-02 | 24 |

**判据 F1**：每个工作步骤在系统中必须可追溯到"谁在什么时候做了、产生了哪条记录"，
否则该步骤等于没有实现。157 个步骤逐条核对。

**判据 F2**：21 张表单（UG-DAF-01～19，含 05A/B/C）每张都要有对应的系统录入与留存，
字段和校验按 UG-DAW-003。局方规定格式的 5 张（表-21-173／174／160／165／166）
**必须使用局方原格式，不得改版式**（手册 0.4.2）。

**判据 F3**：97 类记录每类都要能生成、检索、按 UG-DAW-004 的期限保管和到期处理。
"产生了但无处存"或"存了但查不到"都算未实现。

**判据 F4**：19 项周期性活动由系统调度并提醒，逾期可见；
其中 12 个月上限的两项（独立监督、质量系统内审）逾期即为不符合项，不得静默顺延。

## 四、独立性与职责分离（最容易在软件里做丢的一类）

体系文件把这些写成了**禁止性条款**，软件必须实现为**拒绝**而不是警告。

| # | 约束 | 来源 |
|---|---|---|
| I1 | 独立监督负责人不得由适航管理负责人或其他运行管理人员担任 | 手册 3.1 |
| I2 | CVE 不得核查本人编制或技术审批过的资料 | 手册 3.2、UG-DAP-01 |
| I3 | 编、审、批必须三个不同自然人（体系文件、程序、表单、设计文件） | UG-DAP-01 |
| I4 | CVE 兼任授权人员时，编制人与核查／签署人仍必须不同（至少两人） | UG-DAP-01 |
| I5 | 两名人员不得互为备份并相互核查对方编制的资料 | UG-DAP-03 |
| I6 | 责任部门负责人不得自行验证并关闭本部门的不符合项 | 手册 3.1、UG-DAP-14 |
| I7 | 独立监督负责人不得审核独立监督职能本身 | UG-DAP-13 |
| I8 | 事件报告负责人不得由独立监督负责人兼任 | 手册 3.1 |
| I9 | 任何人不得为自己授权 | UG-DAP-03（DCMS 已实现） |
| I10 | 越权签署无效；签署时校验有效期、专业、具体产品、文件类型 | UG-DAP-03 第 8 节（PR #5 已实现） |

**判据 I-总**：以上每条都要有一个自动化测试，测试内容是"尝试违反并确认被拒绝"，
而不是"正常路径能走通"。这是破坏性测试的做法，不是功能测试的做法。

**设计后果**：岗位不能等同于账号角色。5～8 人编制必然一人多岗，
所以需要**岗位（position）→ 任命（appointment）→ 互斥规则**三层，
让系统能在任命时就拒绝冲突组合，而不是等到签署时才发现。

## 四之二、作业文件的参数是受控配置，不是代码

手册 0.4.1 定了三级文件：上级文件规定"做什么、由谁做、控制要求是什么"，
**第三级作业文件规定"具体怎么做、用什么参数"**，由归口部门负责人批准后生效，按需改版。

软件要实现的恰恰是参数。**如果参数写死在代码里，改一份作业文件就要发一次版本，
三级文件体系在系统里就塌成了一级。**

**判据 P1**：第三级作业文件的参数一律实现为**受控配置数据**，由授权人员在系统中更改，不需要改代码。

**判据 P2**：可配置的边界**正好是文件层级的边界**。

| 出处 | 在系统中 | 更改途径 |
|---|---|---|
| 第一级 手册、第二级 程序 | **固定规则**，代码实现 | 修订属实质性变更，须先获局方认可（UG-DAP-02），随版本发布 |
| 第三级 作业文件 | **受控配置** | 归口部门负责人批准后在系统中更改，留痕 |
| 法规硬时限（第一节 L1～L10） | **固定且不可配置** | 任何人任何角色都不得修改 |
| 独立性约束（第四节 I1～I10） | **固定且不可配置** | 同上 |

法规时限和独立性约束写在手册和程序里（第一、二级），所以天然落在"不可配置"一侧——
这不是额外规定，是文件层级自己推出来的结果。手册 0.4.1 末段已明写："法规和局方程序明确规定的时限
（如 48 小时事件报告、局方不符合项 21 个工作日、质量系统内审 12 个月、独立监督 12 个月、
DOA 证书到期前 3 个月申请延续）写在手册和程序中，**不得通过修订作业文件调整**。"

### 参数清单（13 份作业文件）

| 作业文件 | 可配置参数 |
|---|---|
| UG-DAW-001 工作时限和周期规定 | **153 个内部时限** + **19 项周期活动**频次 |
| UG-DAW-002 文件编码规则 | 体系文件编码格式、局方三张表的编号规则（FL/PZ/SM **三种格式不同**）、项目号格式、**24 个文件代码**、记录编号格式、版次标识 |
| UG-DAW-003 表单填写说明 | 21 张表单的填写要点与易错处（11 行） |
| UG-DAW-004 记录保存期限表 | **97 类记录**的保存期限、保管岗位、载体、到期处理 |
| UG-DAW-005 电子系统操作说明 | **9 种角色的权限矩阵**、权限申请／变更／撤销的办理方式与时限 |
| UG-DAW-006 培训课程和考核要求 | 课程与岗位对应（11 门）、学时、考核方式、合格标准、有效性评估 |
| UG-DAW-007 设计评审要求和检查表 | 三级评审的时机与重点、评审组组成、**三张检查表共 20+ 检查项** |
| UG-DAW-008 设计输出文件类型和编制要求 | **9 类输出文件**是否纳入构型控制、典型编号、各类必含内容 |
| UG-DAW-009 构型标识和基线规则 | 构型项目选取规则、标识规则（6 项）、**互换性判据与换件号规则**、有效性表达、基线内容与时机、构型纪实字段、BOM 结构规则 |
| UG-DAW-010 分类判据使用说明 | **9 条判据**的"显著影响"定义与所需证据（含重量平衡的 kg／%MAC 阈值，现为空）、判定步骤 |
| UG-DAW-011 符合性方法选用 | **MC0～MC9 十种方法**的适用情形与输出文件、CVE 核查要点（7 项） |
| UG-DAW-012 供应商分级和评价准则 | A/B/C **分级判定标准**与定期评价频次、评价项目权重（7 项）、**否决项**、现场审核检查项（8 项） |
| UG-DAW-013 审核检查表 | 独立监督检查表（13 项）、质量系统内审检查表（10 项） |

**判据 P3**：参数变更走文件修订流程，不是"管理员改个设置"。
每次变更记录版次、生效日期、批准人，与所属作业文件的版次对应（UG-DAP-01）。

**判据 P4（关键）**：参数按**生效日期**生效，**历史记录用当时有效的参数评价**。

举例：2027 年把"审核 ≤5 个工作日"改成 7 个工作日，**2026 年那条超期记录不得因此变成合规**。
做不到这一点，改参数就成了篡改历史合规状态——比参数写死更糟。
这要求配置数据保留全部历史版次，且合规判定按记录发生时刻取值。

## 五、已有系统的既成事实（不是从零开始）

UG-DCMS main 分支现状：FastAPI + PostgreSQL + 原生 JS，242 个文件、28 个迁移、80 余张表。

**可直接承载 DAS 要求的：**

| DAS 要求 | 已有实现 |
|---|---|
| 编／审／批三级流转 | `approval_request` / `approval_step` / `approval_round_history` |
| 授权签署人登记册、电子签名 | `signer_authorization` / `signature_record`（含专业与产品范围，PR #5） |
| 记录不得覆盖原值 | `audit_log`、`dcms_block_write` 触发器、授权表的"只能撤销"触发器 |
| 编号唯一不重用、分配台账 | `number_allocation` / `part_number` |
| 构型项目、版次、基线 | `design_object` / `file_revision` / `design_baseline` / `baseline_item` |
| 有效性与贯彻 | `applicability_rule` / `bom_line_applicability` |
| 提醒 | `notification` / `notification_device` |

**结论**：DAS 运行功能应作为同一平台上的模块，不另起系统。理由是授权登记册和构型证据
不能有两份——分叉的那一刻两边都失去可信度。但**独立监督必须是独立权限域**，
`admin` 角色不得有写权限，这是 I6/I7 在系统层面的体现。

## 六之二、非功能要求

来源是 **UG-DAW-005《电子文件管理系统操作说明》**——体系文件中唯一一份直接规定本系统的作业文件，
第 1 章即载明"系统名称／版本 **【UG-DCMS，版本 ____】**"。它不是参考资料，是现成的需求规格。

| # | 输入内容 | 来源 | 可验证判据 |
|---|---|---|---|
| N1 | **系统不可用时，法规时限和紧急止用措施不得等待系统恢复** | UG-DAW-005 第 8 章 | 必须有线下路径：48 小时报告、紧急止用通知在系统宕机时照常执行；恢复后补录并标注实际发生时间与补录时间，两个时间都要保留 |
| N2 | 纸质件与电子件内容必须一致，**以系统中为准**；不一致时登记不符合项并**立即停止使用有疑义的版本** | UG-DAW-005 第 9 章 | 系统是权威副本；发现不一致要能一键登记 NCR 并冻结该版次 |
| N3 | 角色权限**按岗位授予，遵循最小权限** | UG-DAW-005 第 2 章 | 9 种角色的权限矩阵是配置（见四之二）；不得有"超级用户"绕过独立性约束 |
| N4 | 权限申请、变更、撤销有规定的办理方式、批准人和时限 | UG-DAW-005 第 6 章 | 撤销签署权"责任经理决定当日"生效；新权限使用前完成开通（UG-DAW-001） |
| N5 | 影响分析与查询：使用位置／引用关系查询、版本比较 | UG-DAW-005 第 5 章 | 设计更改的影响分析（UG-DAP-06 第 2 步）要能由系统给出受影响对象清单，不靠人工翻 |
| N6 | 备份与恢复：服务器备份每日、可恢复性验证每半年、异地容灾 | UG-DAW-005 第 7 章、UG-DAP-01 第 14 步 | 恢复验证要有记录；验证失败即为不符合项 |
| N7 | 签署留有身份验证和内容摘要，**签署后不得修改，只能升版** | UG-DAP-01 | 已实现（`signature_record.content_sha256` + 密码重输） |
| N8 | 电子记录使用关联的更正记录保留原值、修改人、时间和复核轨迹，**禁止覆盖已签内容** | 手册 0.4.3 | 已部分实现（`audit_log`、`dcms_block_write`）；更正记录的关联关系待实现 |
| N9 | 容量 | 尚无文件依据 | **待定**：现有基准设想为 10 万图号族／100 万件号，DAS 模块的记录量级需另行估算 |

**判据 N-总**：N1 和 N2 合在一起意味着系统**不能是唯一路径**，但必须是**唯一权威**。
这两条看似矛盾，实则一致：允许线下发生，但线下发生的事必须补进系统，且补录后以系统为准。
设计时要把"补录"当成一等公民，不是异常处理。

## 七、取证时序（什么必须先有）

| # | 输入 | 判据 |
|---|---|---|
| C1 | 设计机构许可证编号取证后才有，但批准声明里要用 | 无证编号时，系统必须**阻止**对外发布带批准声明的资料 |
| C2 | 许可项目单界定权利范围，超出即越权 | 小改自批、分类批准必须校验是否在项目单范围内 |
| C3 | 本次申请范围不含修理设计、不含验证试飞（含外包） | 系统不提供这两类流程入口；识别到需求时提示先走 UG-DAP-02 变更范围 |
| C4 | 演练／模拟数据不得当作真实证据 | 演练标记必须在创建时确定且**不可事后改为真实**；演练记录不得进入符合性自评 |
| C5 | 检查单当前 51 条"部分符合"、0 条"符合" | 系统不得因为填写完成而自动改判为"符合"，必须有证据引用才可改 |

### 8.2 M3 项目管理：三条审定路径，不是两条

UG-DAP-09 里类型分支是明写的：第 2 步「首次申请 DOA」、第 3 步「**仅 PMA 项目**」、
第 4 步「**STC 要点核对**」；第 2 步 d 项带出第三类。

| 类型 | 路径要点 |
|---|---|
| **STC** | 立项 → 要点核对（现行审定基础、对适航环保噪声排放的影响、专用条件、对 ICA/AFM/构型的影响、试验件与大纲、交付资料清单）→ 申请 → 审定计划 → 设计与验证 → 符合性声明（表-21-160）→ 取证 → 转段 |
| **PMA** | 立项 → **生产质量系统确认**（CCAR-21.303／21.137，另建体系，未确认不得提交申请）→ 申请（图纸规范、尺寸材料工艺、试验计算报告或相似性论证）→ 验证 → 符合性声明 → 取证 → 转段（项目单 2 年延续归 M10） |
| **设计供应商受托** | 接洽 → 合同／技术协议评审 → 立项 → 接收委托方设计输入并确认充分性 → 验证 → **本单位 CVE 独立核查** → 授权人员签署 → 交付委托方。**不出符合性声明，不对委托方产品作设计批准**（UG-DAP-07 第 12 步） |

**判据 M3-1**：状态机按项目类型参数化，第三类不得复用前两类的"出符合性声明"分支。

### 8.3 两处结构判断

**（一）项目做到"转段"为止，证后挂在"设计批准"上**

UG-DAP-09 第 9 步自己就叫「批准后转段」——移交持续适航（UG-DAP-11）、生产协调（UG-DAP-10）、归档（UG-DAP-01）。

理由是数据归属：证后活动挂在**证件**上而不是项目上。一个产品可能有多个 STC；
ICA 修订、服务通告、适航指令建议、21.99 信息、权益转让（转的是证件）、撤销召回——都按证件走。
项目有结束时间，证件长期有效，PMA 项目单还要每 2 年续。

**做法**：M3 产出一个「设计批准」对象，M8 的活动挂在它上面。
界面上仍可从项目一路点进去，用户感觉不到切分，但数据模型是对的。

**（二）设计更改分类是服务，不是项目的一个阶段**

取证中它是项目内活动（UG-DAP-09 第 7 步引 UG-DAP-06）；取证后它是独立活动，
**而且判为大改时会派生一个新项目**（申请新 STC）。所以 M4 被 M3 调用，不属于 M3。

### 8.4 M2 独立监督与内部审核：是两类活动

UG-DAP-13 第 1 步原文：

> a) 设计保证系统独立监督——周期不超过 12 个月，须覆盖 DOA 符合性检查单的全部适用项；
> b) 质量系统内部审核——间隔最长不超过 12 个月，覆盖质量系统的所有过程、活动和部门，
> 并明确覆盖 CCAR-21 的适用要求（不得仅按 ISO9001/AS9100 实施）。
> 两类计划可合并编制，但**周期和覆盖范围须分别标明**。

**判据 M2-1**：两类活动的覆盖对象不同（检查单适用项 vs 质量系统过程），
模块必须能分别排计划、分别统计覆盖率。合并成一个"内审"会把这个区分做丢，而这正是局方会查的。

**判据 M2-2**：M2 是独立权限域，append-only，被监督对象无写权限，`admin` 角色亦然（I6/I7）。

### 8.5 M1 人员培训与授权：授权是三维的

按 UG-DAM-01-附2 的栏目，授权范围 = **专业 × 批准类型及产品范围 × 可签署文件类型**。

第三维「可签署文件类型」是 5 类**适航签署事项**：
分类（UG-DAF-02）／符合性声明（UG-DAF-03）／制造符合性声明（UG-DAF-12）／
小改批准（UG-DAF-04）／CVE 核查。

**这与 DCMS 现有的 `file_type_code`（DWG 图纸、SPEC 规范、QTP 试验大纲……）完全不是一回事。**
前者是适航签署行为，后者是设计文档种类。见第九之二节。

**判据 M1-1**：三维齐备前，"未列入的产品类别不得签署"（手册 3.2）在系统中不成立，
符合性自评必须如实写明由纸面授权书把关，不得因为界面上有字段就称已实现。

### 8.6 建设顺序

按"先产生取证证据"排，不按技术难度。

| 批次 | 内容 | 理由 |
|---|---|---|
| **第一批** | 符合性检查单（主数据）→ M1 → M6 → M7 → M2 | 取证前必须，产生局方要看的证据 |
| **第二批** | M3（含项目实体）→ M4 → M5 → 时限引擎 → 记录台账 | 取证后半年内 |
| **第三批** | M8、M9、M10、M11 | 可长期先在线下运行 |

第一批的顺序不可颠倒：检查单是锚点，它的数据结构决定其余模块怎么往上挂。
M1 紧随其后，因为 M6／M7／M2 的每一条记录都要落到具体的授权岗位上。

## 九、尚未解决、需要决策的设计问题

1. **授权第三维「可签署文件类型」什么时候能做。** 那 5 类适航签署事项要等 M4（更改分类、
   小改批准）和 M3 的符合性验证部分落地，才有动作可授权。在那之前 M1 的授权模型是不完整的，
   这一点要在符合性自评里写明，不能因为界面上有"文件类型"下拉框就认为已覆盖——
   那个下拉框装的是 DCMS 的文档种类，不是签署事项。
2. **UG-DAF-02 的影响面勾选要不要在系统里强制。** 表单上已有六个判据
   （重量平衡／结构强度／可靠性／系统性能／飞行运行特性／噪声排放），现在是纸面勾选。
   若做成系统必填、且与分类结论联动——勾了"重量平衡"却判小改必须给出理由——
   就能把 UG-DAW-010 的"判据中任一项达到显著影响即为重大更改；无法判定的按重大更改处理"
   落成系统行为而不是一句要求。待定的是"给出理由"够不够，还是应当直接要求授权人员额外签署。
3. **演练模式的隔离粒度。** 整库隔离最安全但要两套环境；行级标记省事但要防止"演练转真实"。
   C4 要求不可事后改，倾向行级标记 + 数据库触发器禁止修改该字段。
4. **岗位出缺的承接人怎么授权。** O3 要求当日指定，但承接人必须满足原岗位资格（I 系列约束）。
   是临时授权还是正式任命，影响审计链的表达。
5. **符合性检查单的证据引用粒度。** 引用到"程序第几步"还是"某条具体记录"。
   前者容易维护但证明力弱，后者证明力强但每次监督都要重新引用。

## 九之二、已考虑并否决的方案

记下来是为了避免以后有人再提一遍。

### 在 BOM 零件上标"专业"——否决

曾打算给零件加 `discipline_code`，想解决三件事，逐条核对后都不成立：

- **签署校验**：签的是文件不是零件。专业标在 `design_file` 上即可，PR #5 已实现。
- **构型核查按专业分派**：UG-DAF-18 的核查项是"参数一致性（图纸↔数模↔BOM↔规范↔工艺）、
  版次一致性、引用标准一致性"和"as-built ↔ as-designed 逐件号比对"，**全表没有专业这一维**。
  它比的是同一个东西在不同地方说得一不一致，与谁负责无关。
- **每个专业都要配 CVE**（手册 3.2）：项目涉及哪些专业，从该项目下文件的专业汇总即可得到，
  是派生数据，不需要在零件上再存一份。

**更重要的是标了会误导：专业归属 ≠ 影响范围。** 一个座椅电源支架归电气还是结构？
改它可能同时影响重量平衡、结构强度和客舱安全。零件上挂一个 `D09 电气系统`
会让系统显得"这是电气的零件"，而真正要拉进来的结构专业被这个标签盖住——
这是给虚假覆盖感背书，比没有更危险。

正确的表达已经在体系文件里：**UG-DAF-02 的影响面是按"影响"勾的，不是按"归属"勾的**，
一次更改可以同时勾多个判据。见上节第 2 条。

另注：DCMS 的零件已有 `object_function`（功能域：承载、密封、照明……），
那是描述零件干什么的，与适航专业分工是两回事，不要混用。迁移 0028 的注释里写明了这一点。

### 授权范围用自由文本表达"产品"——否决

PR #5 最初给 `signer_authorization` 加了自由文本 `product_scope`，对应手册 3.2 的
"授权范围按产品类别分别确定，未列入的产品类别不得签署"和附2 的"【批准类型；产品／型号／件号；限制】"。

**问题**：字段只写入、只显示，`is_authorized()` 从不校验它。也就是说，
手册要求强制执行的一条控制，在系统里是个装饰。这与上一条（零件标专业）是同一种错误——
看起来有控制其实没有，而且它会出现在授权名单上，让审查者以为系统在管。

**根因**：系统没有项目实体，"产品"没有可引用的标识，所以只能写文本；
而文本无法比对，也无法在 M3 落地后自动迁移（"前 6 排座椅电源"转不成 `UG-STC09A26`）。

**处置**：从 PR #5 中移除该字段。等 M3 的项目实体落地后，
用**项目引用**表达产品范围，一次做对，同时覆盖设计供应商受托项目的场景
（受托授权只限该受托项目，不得顺带签自家 STC 的资料）。

在那之前，"未列入的产品类别不得签署"由纸面授权书把关，符合性自评如实写明未由系统实现。
